# 2026-10-22

## 内存暴涨根因与修复（重要）

用户报「运行一段时很耗内存，没几下就把内存耗没了」。定位到根因是我 10-21 把
`IngestQueue` 容量从 20000 提到 200000 的副作用：单条 message 上限 64KB（生产库实测平均 35KB、
最大 7.6MB），旧容量 20000 ≈ 1.28GB、新 200000 ≈ 12.8GB，而部署堆只有 `-Xmx1g` → 一遇突发/落库
跟不上就 OOM。

**第一版修复（有 bug，已推翻）**：把队列换成 `LinkedBlockingQueue` + 字节预算 `MAX_BYTES`，
但「超限分支」里用 `queue.offer(log, 200ms)` 等待——无界队列永远有空位，`offer` 恒返回 true，
字节预算形同虚设（单测证明 10万×64KB 全被接受、堆到 6.4GB）。

**最终修复（`IngestQueue.java`）**：
- 结构上无界的 `LinkedBlockingQueue`，靠「字节预算」做真封顶；
- `offer` 中若 `queuedBytes+size > MAX_BYTES` 或 `size() >= maxCount`，**直接丢弃**（不再尝试 offer）；
- `MAX_BYTES` 默认 200MB，可用 `-Dxtlog.ingest.maxBytes=<字节>` 覆盖；`maxCount` 背压默认 50000；
- `drainTo` 同步回扣字节计数；`/api/logs` 响应新增 `queueBytes` 暴露内存压力。
- **隔离单测证明**：1MB 预算 + 64KB 日志只接受 15 条、丢 99985、128MB 小堆不 OOM（旧设计必 OOM）。

**部署堆默认**：`start.bat` / `start.sh` / `start-bg.bat` / `xtlog.service` 全部由 `-Xms256m -Xmx1g`
提到 `-Xms512m -Xmx2g`（35KB 平均 + 22GB 库 + FTS 索引，1g 偏紧）。

**结论**：根因是「按条数封顶」在大日志下等于无封顶；改为「按字节封顶」才是正确做法。
