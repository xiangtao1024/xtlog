## 性能测试与修复（xtlog-server）

用户要求「把项目跑起来，测试一下性能」。用隔离 data 目录 + 临时 Python 压测脚本（API 级，非浏览器）实测：

### 发现的关键问题
1. **摄入队列静默丢数据（严重）**：`IngestQueue` 是 `ArrayBlockingQueue(20000)`，且 `offer` 满时非 ERROR 直接 drop。
   采集端 130k/s、落库 ~2000/s，10万条丢了约 8万，接口却返回 `accepted=100000`。
2. **落库写者慢**：`@XtScheduled(fixedRate=500)+drainTo(1000)` 上限 ~2000/s；即便放开，瓶颈在
   `DbClient.batchInsert` 逐行映射 + 逐批 prepare/commit/close。裸驱动能 13万/s，APP 仅 ~1.6万/s。

### 修复（已重建 jar）
- `IngestQueue`：容量 200000；非 ERROR 满时 `offer(log,200ms)` 背压，超时仍满才丢弃；ERROR 仍阻塞不丢。
- `IngestController`：`/api/logs` 响应新增 `queueSize`、`droppedTotal`（如实暴露积压/丢弃）。
- `LogBatchWriter`：专用写连接 + 按表缓存 PreparedStatement + **每周期单次 commit**（≤2万条/250ms 一拍，
  带 re-entrancy 守卫与锁冲突时整周期 reoffer 兜底，绝不丢日志）。

### 修复后实测
- 0 丢弃（`final==accepted`）；实时采集（时间戳顺序）落库 **~10万/s**；随机时间戳（回填）随表增大变慢（SQLite 固有）。
- FTS 值得开：count 47ms vs LIKE 485ms（10×）；搜索 22ms vs 28ms。回填 10万条 ~66s，后台不阻塞采集。

### 结论
- 大 SQLite 文件本身不是性能悬崖；文件增长来自数据量 + 保留策略（`retention.months=0` 不清理）。
- 落库必须跟得上采集，否则有界队列再大也会丢。现已靠「快速落库 + 背压 + 如实上报」三重保障。

### 验证产物
- 压测脚本与 bench 文件均已在 /tmp 与项目 perf-test/ 下清理（未留项目根）。
- 改动文件：`IngestQueue.java`、`IngestController.java`、`LogBatchWriter.java`（均在 `src/main/java/top/xtcoder/xtlog/`）。

## 应用列表「有时候很慢」诊断（同日续）

用户问应用列表偶发卡顿。定位根因：

1. **生产库损坏（主因）**：`data/xtlog.db` 与 `data/服务器下载的库/xtlog.db` 两份独立副本都坏，
   `quick_check` 报 `invalid page number`；损坏根页 1984592 属于 `xt_log_fts_202610_docsize`
   （10月 FTS5 影子表），且对基础表 `xt_log_entry_202610` 直接 `GROUP BY` 会抛 `database disk image is malformed`
   → 基础表/索引同样受损。应用列表的 `attachLogStats` 每请求都扫这张表，扫到坏 b-tree 会卡数秒或报错。
   （本地 `data/xtlog.db.corrupt` 3.9GB / 10-13 是既往一次损坏备份，印证生产库曾坏过。）
2. **结构性次因**：`AppController.attachLogStats` 无缓存，翻页/搜索/增删改都重跑跨月表 `GROUP BY app_id` 聚合，随数据量变慢。
3. **可能诱因**：`retention.months=0` 不清理 → 库涨到 22GB+ → 磁盘写满 → 事务中途失败 → 损坏。

### 已修（jar 已重建 16:30）
- `AppController`：给 `attachLogStats` 加 **15s TTL 缓存 + 失败兜底**（单月表损坏跳过、整体异常回退旧缓存），
  交互不再反复扫大表，且即便月表损坏列表也能开（计数略旧但不挂）。

### 待用户在「生产机(192.168.3.228:18080，库在远端)」执行
- 停服 → 备份 `xtlog.db(+wal/shm)` → `sqlite3 xtlog.db ".recover" > recovered.sql` 重建库（.recover 能从损坏库抢救）。
- 设 `retention.months=1~3` 限制增长，防磁盘写满再损坏。
- 恢复后重建受影响月的 FTS 虚表（FTS 影子表已坏）。
