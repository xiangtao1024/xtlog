根因有二：
- (a) 月表 `xt_log_entry_YYYYMM` 上**完全没有索引**，任何排序/计数/范围聚合都是
  全表扫描 + 逐行读多 KB 的 `message` 文本列（3.8GB 库 list 默认要 20~50s）。
- (b) 首页 `overview` 用单条 `SELECT COUNT(*) ..., SUM(CASE WHEN log_time>=? THEN 1 ELSE 0 END)`
  对 UNION ALL 整表聚合，慢且无法走索引。

修复：
- `src/main/java/top/xtcoder/xtlog/config/DataSourceConfig.java`
  - `ensureLogTable` 末尾建 3 个索引：
    `idx_<t>_time(log_time DESC, id DESC)`、
    `idx_<t>_apptime(app_id, log_time DESC, id DESC)`、
    `idx_<t>_leveltime(level, log_time DESC)`。
  - 新增 `ensureLogIndexes(holder)`：列出已有月表并补齐上述索引
    （给已存在的大库做升级用），`initSchema` 里在两次 `ensureLogTable` 后调用。
- `src/main/java/top/xtcoder/xtlog/controller/StatsController.java`
  - `overview()` 拆成两次走索引的 `countLong`（`total` 与 `today`）。
  - `queryTrend` 重写为 `buildTrend(union, now)`，用 `GROUP BY CAST(log_time/86400000)` 范围扫描。
  - 新增 `countLong(String, Object...)` 辅助。
- `web/src/api/index.js`：`axios` timeout 30000 → 60000。

## 迁移到 MySQL 真实排障（★ 重要，全是坑）

用本地 MySQL 5.7（`D:\app\software_delop\database\mysql\mysql-5.7`）起了个一次性实例做真实验证：
`mysqld --initialize-insecure --datadir=<Temp>/xtlog_mysql_test/data` 然后
`mysqld --datadir=... --port=13306 --console`（root 空密码）。验证完已 `mysqladmin shutdown` 关掉。

按踩坑顺序，五个真因：
1. **没驱动**：pom 只有 xtboot + sqlite-jdbc，xtboot 零依赖不自带任何驱动。
   已补 `com.mysql:mysql-connector-j:8.0.33` 与 `org.postgresql:postgresql:42.3.8`
   （离线仓库里都有）。没驱动时 MySQL/PG 根本连不上。
2. **URL 参数被剥离**：xtboot 连接池会去掉 query string，`createDatabaseIfNotExist=true` 不生效，
   报 `Unknown database`。已加 `ensureTargetDatabase()`：MySQL/PG 先连默认库 `CREATE DATABASE IF NOT EXISTS`。
3. **MySQL 不支持 `CREATE INDEX IF NOT EXISTS`**（会语法报错）。
   `DataSourceConfig` 新增 `createIndexIfMissing()`：先按 IF NOT EXISTS 试，失败退回不带 IF NOT EXISTS，
   再失败忽略（索引只是性能，不该阻断主流程）。ensureLogTable / ensureLogIndexes 都改用它。
4. **TEXT 装不下日志**：源库单条 message 最大 7.6MB，MySQL `TEXT` 上限 64KB。
   `mapType()` 对 MySQL 把 `TEXT` → `LONGTEXT`；MySQL/PG 目标批大小降到 200。
   （顺带确认 `max_allowed_packet` 不是瓶颈：该实例 268MB，200 行×7MB 也能过。）
5. **LIMIT/OFFSET 在并发写入下会重复/漏拷**：月表有 `log_time DESC` 覆盖索引，
   无 ORDER BY 的 OFFSET 翻页顺序不稳，采集端还在持续写入时同一行会落进两个批次 →
   目标库主键冲突（报 `Duplicate entry '200' for key 'PRIMARY'`），源库其实 id 全唯一。
   `copyTable()` 改成 **游标分页** `WHERE id > ? ORDER BY id ASC LIMIT ?`，稳定不重不漏。

### 还有两个必须记住的坑
- **同步请求会超时**：拷 8.5 万行（含几十 KB 的 message）要 ~5 分钟，HTTP 请求 60s 就被断，
  响应体是空的（curl 拿不到任何内容，很容易误判成"数据错误"）。
  → 迁移已改为**异步**：`POST /api/migrate` 只启动后台线程并立即返回 `{ok,async,jobId}`；
  新增 `GET /api/migrate/status` 返回 `{running,done,ok,stage,table,copied,summary,target,error}`；
  前端 `SetupView` 每秒轮询，按 stage/table/copied 显示实时进度，完成后才出「关闭 / 切换到新迁移的库」。
- **并发迁移会互相 drop 表**：两个迁移同时跑，后一个的 `DROP TABLE IF EXISTS` 会把前一个刚建的表删掉，
  报 `Table 'xtlogmig.xxx' doesn't exist`。已加 `BUSY` AtomicBoolean 全局互斥，
  `migrate` / `switch` 都会拒绝并发。
- 排障技巧：xtboot 的 `batchInsert` 抛 `RuntimeException("Batch insert failed: SQL")` **带 cause**，
  必须 `rootCause(e)` 剥 cause 链才看得到真因（已在 MigrateController 里加了 `rootCause()` + `printStackTrace()`）。
  另外：**curl `-o _xxx.json` 在本环境可能不覆盖旧文件**，我一度解析到几小时前的旧响应被骗很久——
  验证时宁可把响应当成变量再写新文件。

## 新功能：日志保留月数（retention）

需求：可配置保存几个月的数据；不设置=不限制；设为 N 则只保留最近 N 个月，更早的
`xt_log_entry_YYYYMM` 整表自动删除。

- 存储：新增配置表 `xt_config(k VARCHAR(64) PK, v VARCHAR(200))`，**故意不放 DATETIME 列**
  （各库 DATETIME 写入行为不一致，没必要冒险）。key = `retention.months`，0/空 = 不限制。
  随库走，迁移时会一起被拷到新库。
- `DataSourceConfig` 新增：`ensureConfigTable` / `getConfig` / `setConfig` /
  `readRetentionMonths` / `applyRetention(holder)`（返回被删表名）/ 私有 `monthValueOf`。
  - 保留窗口算法：`current = year*12 + month(0基)`，`cutoff = current - (N-1)`，
    表名折算 `y*12 + (m-1)`，**小于 cutoff 才 DROP**。N=1 只留当月（当月 val==cutoff，不删）。
  - `monthValueOf` 解析失败返回 0 → 跳过（绝不误删非月表/怪名字的表）。
  - `initSchema` 里建配置表；`dbClientHolder()` 启动末尾跑一次 `applyRetention`（未配置时空操作）。
- `service/RetentionCleaner`：`@Component` + `@XtScheduled(fixedRate = 6h)` 定期巡检，
  跨月后自动清理（平时只是比对表名，开销可忽略）。
- `controller/ConfigController`：`GET /api/config` 返回 `{retentionMonths, logTables}`；
  `POST /api/config` 存值并**立即执行**清理，返回 `{ok, retentionMonths, dropped, logTables}`。
- 前端：`api/index.js` 加 `configApi`；`SetupView.vue` 新增「日志保留」card
  （`el-input-number` 0~120、0=不限制、保存、显示被删表列表与当前月表清单）。

验证（当前月 202610）：造了假表 202601/202608 后设 N=2 → 精确删掉这两张、留下 202609/202610；
改 0 → 不删；设 1 → 只留 202610（删 202609，该表本来就是 0 行空表）；
配置重启后仍生效；`initSchema` 会在启动自动重建「当月+上个月」表，所以 202609 重启后回来了。
**已把配置复位为 0（不限制）**，服务在 SQLite 正常运行（日志 85240 条）。
