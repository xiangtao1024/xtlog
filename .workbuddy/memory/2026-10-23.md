## 修复：添加应用报 SQLITE_BUSY（写锁竞争导致的前台报错）

**现象**：生产日志里 `AppController.create` 的 `INSERT INTO app` 与 `LogBatchWriter.flush` 的批量落库
同时报 `SQLITE_BUSY: database is locked`。

**根因**：SQLite 单写者，上一轮给落库写者加的「专用连接 + autoCommit=false + 整周期单提交」有两个坑：
1. 整周期长事务把写锁持有时间从亚毫秒拉到几百毫秒，挡住前台 `app` 建表；
2. `writeGroupsSqlite` 只 `catch(SQLException)`，一旦 `bindRow` 抛非 SQL 异常（字段类型转换等），
   事务不回滚 → 专用连接**永久持有写锁** → 所有写操作（含写者自己下一轮）都 SQLITE_BUSY 直到 60s 超时。
   叠加全局 `busy_timeout=60000`：竞争方不是重试，而是干等 60s 才报错，错误直接甩给用户。

**修复**（`src/main/java/top/xtcoder/xtlog/`）：
- 新增 `util/DbBusyRetry.java`：通用「写锁竞争重试」工具（识别 busy/locked，短暂退避后重试）。
- `LogBatchWriter.java`：改为**逐组（每张月表）提交**（单表突发等价于一次提交，性能不变，但锁只在单组写入期间被占）；
  加 `catch(Throwable)` 兜底，**任何异常都 rollback + 重置 autoCommit**，且只重入队「未提交的组」杜绝重复/泄漏；
  专用连接设 `PRAGMA busy_timeout=3000`，抢不到锁就快速让步重入队，而非阻塞 60s。
- `DataSourceConfig.sqliteUrl()`：`busy_timeout` 60000 → **10000**（覆盖正常短暂竞争，又不干等数十秒）。
- `AppController.java`：应用 `create/update/delete` 的写操作包 `DbBusyRetry.retry(...)`，瞬时锁竞争自动重试成功，不再报错。

**验证**（隔离 data 目录 API 级压测）：持续 12s 灌入 **172 万条**日志（落库写者近乎常驻占锁），
期间并发创建 30 个应用 → **30/30 OK、0 失败**，延迟 avg 0.17s / max 0.45s；写锁泄漏兜底从未触发。
改动文件：`util/DbBusyRetry.java`(新)、`ingest/LogBatchWriter.java`、`config/DataSourceConfig.java`、`controller/AppController.java`。临时压测脚本已清理。

> 注：此前已确认生产副本 `xt_log_entry_202610` 及其 FTS 影子表 b-tree **损坏**（两份副本 quick_check 一致），
> 这是「应用列表偶发卡顿」的另一主因；根治仍需在生产机 `.recover` 恢复 + 设 `retention.months` 限制增长。

## 修复：当前月表 `xt_log_entry_202610` 主库文件损坏 → FTS 报错刷屏

**现象**（用户贴的服务器日志）：每 10s 刷 `fts bulk insert failed, fallback per-row: ... INSERT INTO xt_log_fts_202610...`，
且 `xt_log_entry_202610` 的任何全表扫描都失败。

**确认**（只读探针，未改库）：`SELECT count(*) FROM xt_log_entry_202610` → `database disk image is malformed`；
`immutable=1`（只看主文件、忽略 WAL）同样 malformed → **损坏在主库文件本身，不是 WAL**。爆炸半径干净：
仅 `xt_log_entry_202610` 坏；`app`(9)、`xt_log_entry_202609`(空)、`xt_fts_state`、`xt_fts_skip` 均正常。
FTS 报错只是症状（回填从坏表读数据 → 抛 malformed → 逐行兜底也失败 → 记 skip → 水位照推），代码已优雅降级不崩。

**处理（用户选「十月表重置」，丢弃十月、保留其余）**：
- 先备份：`data/xtlog.db` + `-wal` + `-shm` → `*.bak20261023`。
- 直连 `DROP TABLE` 失败（malformed 页无法释放）→ 走 salvage：把全部完好表
  （app/category/xt_user/xt_config/xt_datasource/xt_migrate_job/xt_fts_state/xt_fts_skip/xt_log_entry_202609）
  拷进全新干净库 `xtlog.db.new`，**排除** `xt_log_entry_202610` 与其 FTS 全部表。新库 `integrity_check=ok`。
- 交换：`xtlog.db`→`xtlog.db.corrupt-prereset`（10.7GB，侧存），旧 `-wal/-shm` 改名侧存，`xtlog.db.new`→`xtlog.db`（仅 65KB）。
- 重启服务：`initSchema` 的 `ensureLogTable` 自动重建空 `xt_log_entry_202610` + 索引，indexer 重建 `xt_log_fts_202610`。
- 验证：日志无 `fts bulk / busy / malformed`；`integrity_check=ok`；十月表复活并已落 25 条；FTS 报错停。

**结论**：本地 `data/xtlog.db` 已恢复健康。生产机（浏览器连 192.168.3.228:18080 是另一实例）若有同样损坏需同样 salvage。
`data/xtlog.db.bak20261023` 是可回滚的修复前备份；`xtlog.db.corrupt-prereset` 与 `xtlog.db.corrupt`(10-13) 可删（占 ~14GB）。

## 现象：CMD 采集器重复「started」刷屏（非 bug）

`app=2/3` 是 CMD 类型、命令 `journalctl -f -u ksh-xxx`，在 **Windows 开发机**上 `journalctl` 不存在 →
`cmd.exe /c journalctl ...` 立刻退出 → `reconcile` 每 5s 按退避重启 → 无限 `CMD collector started` 刷屏。
属**环境/配置问题**（这些 journalctl 命令只应在 Linux 生产机跑），不是代码 bug；生产机若 unit 存在则正常。
可改进项（未做，待确认）：识别「进程秒级反复退出」的崩溃循环，改为打一次 WARNING 并加大退避，避免刷屏。
