## 日志采集格式要求澄清（用户问答）
- 用户确认诉求：**任意日志都能采集、不丢数据即可**；合不合并成一条都行，**唯一硬要求是「单条落库不要太大」**。
- 现有行为（LogTextIngestor）：一行文本只有「含可识别时间戳」或「首词是级别词」才被判定为新条目；否则当作续行拼到上一条。
  - 纯打印/无时间/无级别文本 → 被合并（直到出现带时间/级别的行才断开），时间记成接收时刻，级别默认 INFO（文本含 error/warn 等词会误判）。**不会丢数据**。
  - 命令通道 pushLine 有 256KB 缓冲安全阀；文件通道 ingestText 整块切分无此上限（理论内存风险，但与单条大小无关）。
- 结论：采集对格式零要求，纯打印能采；只是时间/级别是兜底值、粒度可能合并。

## 关键加固：单条大小保证钉死（DataSourceConfig.readMaxChars）
- 原实现 `n < 0 ? 0 : n` 的隐患：**显式配置 ingest.maxChars=0/负数会返回 0**，而 LogSplitter 把 `maxChars<=0` 视为「不限制拆分」→ 超大单行（如 7MB 堆栈）原样入库，7MB 巨行会复活。
- 改为 `n <= 0 ? DEFAULT_MAX_CHARS : n`：任何 <=0（含显式 0）一律回退默认 64KB；只有真正的正整数才生效（保留用户调大的能力）。
- 配合 LogSplitter.expand（FILE/CMD 的 emit、HTTP 的 pushOne 都调用）落库每段 ≤64KB，至此「单条别太大」在任何配置下都不可被绕过。
