### 本轮修复的问题
1. **编译错误 A**：`FileCollector.scan()` 调用了不存在的 `AppService.getTokenMap()`。
   → 在 AppService 增加 `public Collection<AppInfo> getAllApps()`（空集自动 loadAll），FileCollector 改调它。
2. **编译错误 B**：`SetupController` 里 `holder.replace(newHolder)` 传的是 `DbClientHolder`，而 `DbClientHolder.replace()` 只接受 `DbClient` 或 `SimpleConnectionPool`。
   → 改为 `holder.replace(db)`（initSchema 仍用临时 `new DbClientHolder(db)` 跑）。
3. **启动致命错误**：`SQL execute failed: PRAGMA journal_mode=WAL`。SQLite 的 PRAGMA 既不能一律走 `executeUpdate` 也不能一律走 `executeQuery`：
   - `journal_mode=WAL` **返回结果集** → executeUpdate 抛 `Query returns results`
   - `synchronous=NORMAL` **不返回结果集** → executeQuery 抛 `Query does not return results`
   → 正解：**把 PRAGMA 写进 JDBC URL 参数**（驱动会对每个连接生效），代码里不再显式执行 PRAGMA。
     默认 URL：`jdbc:sqlite:{DB_DIR}/xtlog.db?busy_timeout=5000&journal_mode=WAL&synchronous=NORMAL`。
     注意 `synchronous` 是**连接级**设置，写在 URL 里才对连接池的每条连接生效。

## 第二轮：跨月历史 UNION 查询 + 月分表路由 bug 修复

### 修复的 bug（重要）
- **月分表路由失效**：`LogBatchWriter` 用 `ts instanceof Number` 判定 `log_time` 所属月份，但
  `IngestController` 存的是 `new Date(logTime)`（`java.util.Date`）→ 判定恒为 false → **所有日志都落到「当前月」表**，
  历史/补录日志的月分表形同失效（实测：把 7 月的日志灌进去，查 7 月表查不到，实际写进了 202609）。
  → 改为同时兼容 `Number` 与 `Date`（`((Date) ts).getTime()`）。**存 Date 是对的**（MySQL/PG 的 DATETIME 列需要日期类型），错的只是路由判定。
- 顺带消除「每条日志执行一次 `CREATE TABLE IF NOT EXISTS`」：用 `Set<String> ensuredTables` 按批去重。

### 新增能力
- `DataSourceConfig.monthsBetween(start,end)`：把时间范围翻译成月表名集合（`yyyyMM` 升序去重）。
- `DataSourceConfig.listLogTables(holder)`：列出真实存在的月表（SQLite 查 `sqlite_master`，其它方言回退 `information_schema`）。
- `LogQueryController.query`：跨月 `UNION ALL` + **复合游标 `logTime_id`**。
  - 为什么必须复合：不同月表的自增 id 会重复，单靠 id 无法唯一定位，也不能用 OFFSET。
  - SQL：`SELECT * FROM (t1 UNION ALL t2 ...) t WHERE ... AND (log_time < ? OR (log_time = ? AND id < ?)) ORDER BY log_time DESC, id DESC LIMIT ?`
  - 响应新增 `scannedTables`（本次实际扫了哪些月表），便于前端展示与排查。
  - 默认范围（不传 startTime/endTime）= 当前月 + 上个月。

### 验证结果
- 灌入 7 月日志（ts=1784080800000）→ 落到 `xt_log_entry_202607`；灌入 8 月日志 → 落到 `xt_log_entry_202608`。
- 查「仅 7 月范围」→ `scannedTables=[xt_log_entry_202607]`，只命中 7 月数据。
- 查「7~9 月范围」→ 三表合并，跨月 id 重复仍按 `log_time DESC, id DESC` 正确排序。
- 默认范围 → 只扫 202608 + 202609。**跨月查询闭环打通。**

### 顺手修的
- `AppService` 增加 `volatile boolean loaded` 标记，不再用 `map.isEmpty()` 当「未加载」哨兵
  （应用表为空时会退化成每次调用都查库）。
- `getAllApps()` 改返回 `idMap.values()`，避免漏掉 token 为空的应用（文件采集场景）。

## 第三轮：前端 Vue3 工程 + 浏览器端到端验证（全部通过）

### 工程位置与三条硬约定
前端在 `E:\workspace\xt\xtlog-server\web`（Vue3 + Vite5 + Element Plus + vue-router + axios，无 Pinia，用模块级 ref 做轻量 store）。
1. **静态资源前缀固定 `/static`**（`EmbeddedHttpServer.staticUrlPrefix` 硬编码，**无配置项**）→ `vite.config.js` 必须 `base: '/static/'`。
2. **构建产物直接落到 `../src/main/resources/static`**（`emptyOutDir: true`），与 PCAS 单 jar 约定一致，`mvn package` 自动打进 jar。
3. **路由 base 用 `/`**（不是 `import.meta.env.BASE_URL`）。因为 SPA 回退由后端 `DispatcherHandler` 提供，
   它从 classpath 取 `static/index.html`，且会排除 `/api/` 前缀与带扩展名的路径 → history 路由可直接用 `/logs`、`/apps`。
   注意回退要求请求带 `Accept: text/html`，所以 `curl /` 不带 Accept 会 404，属正常。

### 踩坑（都真实发生）
- **`LogView.vue` 里 `watch` 未导入**：Rollup 对**未声明的标识符按全局变量处理、不报错**，构建成功但运行时
  `ReferenceError: watch is not defined` → 整个 Vue 应用白屏。教训：前端「构建成功」≠「能跑」，必须真机/无头浏览器验证。
- **Edit 工具报「成功」但没落盘**：改 `import { ... watch } from 'vue'` 时第一次报成功，实际文件未变（可能是并发写）。
  → **改完必须用 Grep 复核**，别信单次返回值。
- **中文乱码是假警报**：用 PowerShell `WebClient.DownloadString` 读接口会按系统 ANSI(GBK) 解码 → 看到 `鏀粯缃戝叧`。
  实测**响应原始字节是正确 UTF-8**（框架 `DispatcherHandler:624` 用 `new String(bytes, UTF_8)` 解请求体，响应也强制 UTF-8）。
  **取编码真值必须落原始字节**：`WebClient.DownloadData` + `File.WriteAllBytes` 再读文件。
  唯一真乱码的是浏览器里那条 `REALTIME-PUSH-A` 后面跟的中文 —— 因为它是用 **Git-Bash curl** 发的（GBK 字节），
