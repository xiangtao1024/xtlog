### 后端：`AnalysisController`（新增）

四个接口，公共参数 `appId`（`all` 或具体 id）/ `from` / `to`（毫秒）/ `levels`（逗号分隔）/ `keyword`：

| 接口 | 作用 |
|---|---|
| `GET /api/analysis/overview` | 总数、各级别数、错误率、来源 IP 数、logger 数、首末次时间、扫描月表数、`appName` |
| `GET /api/analysis/trend` | 时间序列，`bucket = hour \| day`，每桶 total/error/warn |
| `GET /api/analysis/breakdown` | 维度 Top N，`dim = level \| logger \| ip \| thread` |
| `GET /api/analysis/patterns` | 错误聚类（见下） |

**执行策略（必须沿用）**：按月表分别聚合 → Java 侧合并。
绝不能 `SELECT ... FROM (UNION ALL 全列)`——MySQL/PG 会把派生表连同 LONGTEXT 一起物化，代价极高。
这与 `LogQueryController` 检索优化验证过的写法一致。

**★ 跨方言的坑：时间列不能做算术**
`log_time` 在 SQLite 里是 **epoch 毫秒长整型**，迁移到 MySQL/PG 后是 **DATETIME/TIMESTAMP**。
所以分桶表达式必须按方言生成，不能写 `log_time/3600000`：

- MySQL → `DATE_FORMAT(log_time, '%Y-%m-%d %H:00')`
- PostgreSQL → `to_char(log_time, 'YYYY-MM-DD HH24:00')`
- SQLite → `strftime('%Y-%m-%d %H:00', log_time/1000, 'unixepoch', 'localtime')`

`bucketExpr()` 用 `DataSourceConfig.isMySql/isPg` 判断；桶 key 是字符串 label，字典序即时间序。
`toLong()` 做成宽松读取（MySQL 的 COUNT 可能返回 BigDecimal）。

### 错误聚类（patterns）的两阶段实现

message 平均 46KB、最大 7.6MB，**绝不能整批拉进内存**：

1. 阶段一：只 `SELECT id, log_time ... WHERE level IN ('ERROR','WARN') ORDER BY log_time DESC, id DESC LIMIT scan`，
   跨月表归并取最新 `scan`（默认 5000，上限 50000，`scan` 参数可调）条；
2. 阶段二：按表分组 `id IN (...)` 分批（400/批）回捞 `substr(message,1,400)`；
3. Java 侧 `firstLine()` 取首行 + `normalize()` 归一化后聚合。

`normalize()` 规则（顺序敏感）：时间戳→`<ts>`、UUID→`<uuid>`、`0x..`→`<hex>`、
带点数字→`#`、纯数字→`#`、单/双引号串→`'#'`/`"#"`、空白折叠、截断 160 字符。

实测效果（本机 8.9 万条真实日志）非常好：
`调用AI接口异常，政策ID: #` 470 次、`<ts> [pool-#-thread-#] ERROR ...` 370 次、`Parameter should either be a simple or a content type` 330 次（跨 3 个 IP 合并成一类）。

## 修复：切到 MySQL 数据源后「应用列表 500 —— LocalDateTime cannot be cast to Number」

根因同属一类（时间列跨方言）：`attachLogStats` 里 `MAX(log_time)` 的值被直接
`(Number) d.get("mt")` 强转。SQLite 存 epoch 毫秒（Long）能转；MySQL 驱动返回
`java.time.LocalDateTime` → CCE。

**统一收敛：所有读时间/数值的地方都走 `DataSourceConfig.tsOf(o, 0L)`，**
写的地方都走 `DataSourceConfig.tsValue(holder, ms)`。已替换 4 个控制器里的本地
`toLong` / 强转：AppController(MAX(log_time))、AnalysisController、LogQueryController、
StatsController。

顺带修掉一个**静默错误**：`AnalysisController.buildCond` / `LogQueryController` 的
`log_time >= ?` 原先一律绑 Long，MySQL 的 DATETIME 与整数比较永远不成立 →
切到 MySQL 后分析页查出来 **total=0**（不报错，很难发现）。现改为按方言绑 Timestamp。

**前端同步**：MySQL 下 `create_time` 序列化成 `"2026-10-09T14:48:55"`（不是毫秒数字），
`web/src/utils/format.js` 新增 `toDate()`，同时支持毫秒数与 ISO / "yyyy-MM-dd HH:mm:ss.SSS" 串，
保证换库后时间列照常显示。

**教训（务必遵守）**：xtlog 支持 SQLite / MySQL / PG 三种数据源，任何涉及时间列的
读(`tsOf`)、写(`tsValue`)、比较(`tsValue` 绑参)、分桶表达式(`bucketExpr`) 都必须走
`DataSourceConfig` 的方言辅助，禁止裸强转或裸绑 Long。
排查这类问题的套路：`tsOf` 支持 Number/Date/LocalDateTime/LocalDate/Instant/OffsetDateTime/
ZonedDateTime/String 全部形态，直接用它最省事。

## 关键词检索提速：SQLite FTS5 trigram 全文索引（已完成）

**问题**：9.5 万行的库却有 3.2GB message（平均 35KB、最大 7.6MB），
`LIKE '%kw%'` 无索引可用，每次检索通读 3.2GB 文本：**COUNT 3.5~8.3s**、
关键词 0 命中时首屏 **6s**（走时间索引的 early stop 只对"有命中"有效）。

**方案**（用户选定）：FTS5 + `tokenize='trigram'` 外部内容表
（`content='<月表>', content_rowid='id'`，只存倒排不复制正文）。
trigram 切连续 3 字符，语义等价于子串匹配，实测与 LIKE **结果完全一致**。

**实测数据**（4GB 库 / 95351 行）：

| 关键词 | 开启前 | 开启后 |
|---|---|---|
| ERROR | 7.51s | 0.09s |
| timeout | 7.15s | 0.015s |
| 调用AI接口 | 4.31s | 0.029s |
| 异常（2字） | 4.69s | 4.28s（回退 LIKE，trigram 硬限制） |

单表 COUNT 对比：FTS 0.003~0.024s vs LIKE 4.2~5.3s（**222x ~ 1783x**）。
索引实际体积 **1.17GB**（不是按抽样外推的 5.2GB——真实日志重复度高，压缩率远超预期）。

**新增文件**：
- `service/FtsService.java` — 开关/水位/建表/回填/状态。FTS 表命名 `xt_log_fts_YYYYMM`
  （**故意不叫 xt_log_entry_*，否则会被 listLogTables 当成年表**）。
- `service/FtsIndexer.java` — `@XtScheduled(fixedRate=10000)` 增量回填。
- `controller/FtsController.java` — `GET /api/fts/status`、`POST /api/fts/toggle`。
- 前端：`ftsApi` + SetupView 新增「全文索引」Tab（开关/进度条/原理说明）。

**关键坑（都踩过）**：
1. **回填必须按「文本量」切批，不能按行数**：message 大小差 3 个数量级，
   按 300 行切批遇到巨行时事务几十秒，占死 WAL 写锁 → 日志落库 `SQLITE_BUSY` 失败丢日志。
   改为先用 `SELECT id, LENGTH(message)`（走主键、长度从行头拿不读 overflow 页）
   累计到 `BATCH_CHARS=12M` 切批；同时 `sqliteUrl()` 的 busy_timeout 5000→30000，
   `LogBatchWriter` 加 3 次重试。改完 BUSY=0。
2. **查询要拆两条 SQL**：段一 `id IN (SELECT rowid FROM fts WHERE message MATCH ?)` +
   段二 `id > 水位 AND message LIKE ?`（兜住未回填的新日志），Java 侧归并。
   合成一条 `OR` 会让优化器放弃索引顺序扫描、丢掉 early stop。
3. **trigram 最少 3 字符**：2 字中文（"异常"）切不出 token → MATCH 恒为 0，
   必须 `keyword.length() >= 3` 才走 FTS，否则回退 LIKE。前端给了
   "关键词过短，未走索引" 的 chip 提示。
4. `INSERT INTO fts(fts) VALUES('automerge=0')` 在 python 驱动下报 SQL logic error，
   且 automerge **不是** CREATE VIRTUAL TABLE 选项 → 没用上，靠加大批次解决。
5. external content FTS 表的 `COUNT(1)` 直接读 content 表，**不能用来判断是否已索引**，
   进度只能看水位表 `xt_fts_state`。
6. 一次性 `INSERT INTO fts(fts) VALUES('rebuild')` 全量构建 **409s**（6.8 分钟），
   但它是长事务，会占死写锁 → 生产用分批（锁友好），首次构建预计 10~20 分钟，
   期间结果仍完整（已索引段走 FTS、尾段走 LIKE）。建完后增量 200 行仅 **0.01s**，完全跟得上写入。
7. 切数据源后 `xt_fts_state` 要在新库重建 → `ensureStateTable` 用 `stateHolder == holder`
   比对重置缓存。保留策略删月表时 `applyRetention` 会同步 `FtsService.dropFor`。

**状态**：已开启并验证；`dist/xtlog-server-0.0.1.tar.gz` / `.zip` 已刷新。
遗留：① 2 字关键词仍慢（无解，只能提示）；② AnalysisController 的关键词聚合未接入 FTS。

## 架构评估：SQLite 存元数据 + Lucene 存日志？（已做实测，**建议不做**）

用户提问：把多数据源切换改成「SQLite 存基本数据 + Lucene 存日志，配一个数据目录」，
是否会有质的提升。用真实数据做了 Lucene 8.9.0 基准（未写入项目代码，临时代码已删）。

### 数据画像（决定一切的前提）
95792 行 / 正文 3180MB，**平均 34.8KB、最大 7.67MB**，分布严重畸形：

| 区间 | 行数 | 占比 |
|---|---|---|
| <=4KB | 65599 | 68.5% |
| 4K~64K | 20595 | 21.5% |
| 64K~1M | 9387 | 9.8% |
| **>1MB** | **211** | **0.22%，却占 1046MB（33% 体积），平均 4.96MB** |

### Lucene 实测（抽样 5054 doc / 160MB 正文，线性外推全量）
膨胀比 = 索引体积 / 原文体积：

| 方案 | 膨胀比 | 全量外推 | 2字中文 | 构建速度 |
|---|---|---|---|---|
| **FTS5 trigram（现状）** | 0.37x | 1.17GB | ❌ 回退 LIKE 4.28s | rebuild 409s |
| Lucene trigram 不存原文 | 1.04x | 3.3GB | ❌ 不可召回 | 17.3 MB/s |
| Lucene trigram 存原文 | — | ~4.5GB | ❌ | — |
| Lucene **ngram(2,3)** 不存原文 | **3.95x** | **12.6GB** | ✅ 0.0005s | 6.8 MB/s |
| Lucene ngram(2,3) 存原文 | 4.35x | 13.8GB | ✅ | 6.0 MB/s |

StoredField 压缩实测 160MB→约 60MB（2.7:1），所以「用 Lucene 替掉 SQLite 存正文」
体积上可行，但 Lucene 检索层本身比 FTS5 贵得多。

查询延迟：Lucene 全部 0.0002~0.019s（5% 样本，全量后估计 0.002~0.05s，仍亚秒）。
**但现状 FTS5 全量已经是 0.015~0.09s —— 同属"感知即时"区间，用户感觉不到差别。**

### 结论
1. **查询速度：不会有质的提升。** 唯一数量级差异是 2 字中文（异常 4.28s → 0.0005s），
   代价是索引从 3.3GB 涨到 12.6GB（+9.3GB）。为这一个短板付这个价钱不划算。
2. **真正的收益在架构简洁**：现状 63 处方言分支散布 9 个文件 4104 行，
   其中 MigrateController(846) + DataSourceConfig(760) 几乎纯为多库兼容而生。
3. **最大隐性成本**：AnalysisController(776 行) 的 SQL GROUP BY 聚合要改写为 Lucene
   faceting（SortedDocValues + FacetsCollector），灵活性远不如 SQL；
   写入链路要重做 NRT refresh / merge / 软删除；运维从「单文件 sqlite3 可开」
   变成「多 segment 目录 + CheckIndex 恢复」。

### ★ 真正的瓶颈其实是数据畸形，不是数据库选型
截断到前 **64KB** 只损失 **0.1%~0.4% 召回**（关键词几乎都落在开头），
却能砍掉 **73% 正文**（3180MB → 862MB），进而让 FTS5 索引从 1.17GB 降到 ~319MB。
**在采集侧限制单条日志上限，比换任何存储引擎的性价比都高。**

### 建议路径
- 当前（10万行/3GB）：**不换**。投入产出比很差。
- 若确实要 Lucene：**双写保留**（SQLite 作 source of truth + Lucene 作检索层），
  只替换关键词检索一条路径，聚合/写入/备份全不动，风险可控可回滚。
- 触发全量替换的信号：千万行级 / 需要 DSL 检索语法 / 需横向扩展
  → 那时应直接上 Elasticsearch，而非裸 Lucene。

## 超长日志分片存储（已完成）

需求：单条日志设上限，**超限不截断尾部**，而是拆成多条保存，并标记「这条是上一条的继续」。

### 数据模型（月表新增两列）
- `cont_group` VARCHAR(32)：同一条原始日志的所有片段共享；未拆分的为 **NULL**
- `cont_seq` INT：0 起，0 = 首段，>0 = 第几段续篇
- 索引 `idx_<月表>_grp (cont_group, cont_seq)`。未拆分的行 group 是 NULL，
  **NULL 不进索引**，所以这个索引几乎只装真正被拆的行，体积可忽略。

**为什么用「组+序号」而不是「指向上一条 id」**：批量写入时拿不到自增 id，
链式写法需要串行插入；组+序号在写之前就能确定，一次 WHERE cont_group=? 就能取回整组，
还能顺带知道总段数。

老库兼容：靠 `ensureLogTable` 里已有的 `addColumnIfMissing` 自动补列（已验证 202609/202610 两张老表都补上了）。

### 改动文件
- **新增** `ingest/LogSplitter.java`：`split()` 优先在换行处断开、单行超上限才硬切（防止段无限增大/死循环）；
  `expand()` 生成 cont_group/cont_seq。**未超限也会写这两个 key（值为 null/0）**——
  同一批 Dict 的 key 集合必须一致，否则 batchInsert 可能按首条组装列名让后续行写不进去。
- **新增** `service/IngestConfig.java`：@Component，5 秒 TTL 缓存 `ingest.maxChars`，避免每条日志都查配置表。
- 接入点：`IngestController.pushOne` 与 `LogTextIngestor.emit`（HTTP/FILE/CMD 三通道全覆盖）。
  **放在入队前而不是 LogBatchWriter**：这样 LogBroadcast 实时推送到的也是分片结果，两条链路天然一致。
- `DataSourceConfig`：KEY_MAX_CHARS / DEFAULT_MAX_CHARS(65536) / readMaxChars + 月表补列补索引。
- `ConfigController`：`/api/config` 读写 maxChars（下限 4096，0=不限制），保存后调 `IngestConfig.invalidate()` 立即失效缓存。
- `LogQueryController`：COLUMNS 加两列 + **`GET /api/logs/group?g=&ts=`**（ts 可选，带上就只查那张月表，
  省去遍历所有月表）；返回 segments / count / message（拼接好的全文）。
- 前端：`LogConsole` 行头加琥珀色「续 N」角标 + 详情弹窗「查看完整日志」按钮（拼好后也是复制的对象）；
  `LogView` 表格同样加角标；`SetupView` 的「日志保留」Tab 改名「日志策略」，加 maxChars 输入。
- `utils/format.js`：`toDate` 原本没 export，已加（LogConsole 要用它把 log_time 转毫秒传给 group 接口）。

### SQLITE_BUSY 批量落库丢日志修复（10/15 下午）
- **现象**：远程 Linux 上 `LogBatchWriter.flush()` 批量 INSERT `xt_log_entry_202610` 反复报
  `[SQLITE_BUSY] database is locked`，每 ~15~30s 一次，且失败后被丢弃（"log batch insert failed"）。
- **根因**：SQLite 只允许一个写者。FTS 后台回填（`FtsIndexer` 每 10s）开写事务时与日志落库抢同一把锁：
  原 `BATCH_CHARS=12MB` 单批事务要 tokenize 最多 12MB 文本（7.6MB 巨行独占一个事务），持锁几十秒、
  批间只让 40ms，落库端的 `busy_timeout=30s` 被撑爆 → 失败丢日志。
- **改动**：
  - `FtsService.BATCH_CHARS` 12MB → **2MB**（单批亚秒~1-2s 即放锁）。
  - `FtsIndexer`：`MAX_BATCHES_PER_TICK` 20→**4**、`PAUSE_MS` 40→**120ms**，并新增
    **摄入队列积压 >1000 立刻收手让锁**给实时落库（索引可以慢建，日志一秒不能丢）。
  - `DataSourceConfig.sqliteUrl()`：`busy_timeout` 30s → **60s**（落库端通常「等一下」就拿锁，少走重入队）。
  - `LogBatchWriter`：撞锁（SQLITE_BUSY/locked）**不再丢**，改为放回队头下个 500ms 周期重试
    （`retryBuffer` + `isLockContention` 判异常链）；非锁类错误才记失败放弃。落库端变成「至多延迟、绝不丢失」。
- **验证**（本地隔离实例 + 并发压测）：开 FTS 后连续 30~40s 推送日志（含直接注入的 10 行 7MB 巨行制造最坏回填），
  结果 **pushed == stored（cont_seq=0 去重后），lost=0**；`SQLITE_BUSY/failed/deferred/yields` 全 0
  —— 巨行回填被 60s busy_timeout 直接吸收，无需触发重入队。代码已 `mvn -s _mvn-settings.xml package` 通过，
  本地 dev 服务（E:/workspace/xt/xtlog-server/data，18080）已用新 jar 重启。
- **部署提示**：远程机器要重发 `target/xtlog-server.jar` 才生效；`fts.enabled=1` 时首轮回填会变慢（约 2.5min/1.17GB），
  但查询侧未索引尾段自动回退 LIKE，体验平滑、不再丢日志。

## ★ 修复：FTS 回填「一条都索引不进去」+ 生产卡死根因（10/15 晚）

用户反馈：更新后开了全文索引，跑了一部分停止了，点关闭重跑也不行；把生产库下载到
`服务器下载的库/xtlog.db`（11GB，下载时 WAL 未刷完，全表扫描会报 `database disk image is malformed`，属正常）。

### 根因（两层）
1. **真正的卡死元凶 = 错误的幂等去重条件**（不是 7MB 巨行本身）：
   `buildBatch` 原先写
   `INSERT INTO fts(rowid,message) SELECT id,message FROM log WHERE ... AND id NOT IN (SELECT rowid FROM fts WHERE rowid>=? AND rowid<=?)`
   **对外部内容 FTS5 表，这个 NOT IN 是 BUG**：外部内容表的 `SELECT rowid FROM fts`
   返回的是「内容表」的全部行（含未索引的），不是「已索引」行——这是 FTS5 外部内容表的已知诡异特性
   （已用 Python sqlite3 实测确认：`SELECT rowid FROM fts` 在只索引了 1~10 行时仍返回 1~20）。
   于是 `id NOT IN (...)` 恒为假 → **批量插入一条都插不进去** → 全文索引永远是空的，
   表现为「开了索引但查不到、重跑也没用」。这才是「跑一部分停了 + 重跑也不行」的真因。
2. 7MB 巨行本身**插得进 FTS5、不报错**（实测 0.09s~3.98s，含栈轨迹+base64 真实内容），
   但旧实现没有「巨行跳过」逻辑，遇到连续 7MB 巨块可能抛错/卡住、且水位不前进 → 无限重试。
   生产水位卡在 17437、巨块从 17435 起，与之吻合。

### 修复（`FtsService.buildBatch`）
- **删掉两处 `NOT IN (SELECT rowid FROM fts ...)`**，改成纯批量插：
  `INSERT INTO fts(rowid,message) SELECT id,message FROM log WHERE id>? AND id<=? AND LENGTH(message)<=?`
- 幂等改靠「**水位单调**」保证：正常流程每个 (表,id) 只处理一次；即便水位持久化偶发失败导致重放，
  外部内容表对同 rowid 重插**不会产生重复项**（实测 MATCH 仍只命中一次，Test3-A/C/D 均验证）。
- 巨行（>MAX_FTS_DOC_CHARS=1MB）一律 `recordSkip` 进 `xt_fts_skip`、不进索引，查询时走 LIKE 兜底；
  水位**无条件前进**（setWatermark 在批末恒调用）→ 连续巨块被整批记 skip、水位直接越过，**永不卡死**。

### 验证（端到端，真实服务器 + 复现数据）
脚本：直接 SQL 往当月月表插 460 行 = 200 普通(`NORMALHOOK`) + 60×7MB 巨行(`GIANTHOOK`) + 200 普通(`ALPHAMARK`)
（**务必直接插 7MB 单行使**——走 HTTP 摄入会被 `LogSplitter` 拆成 64KB 段，复现不出巨块）。
重启开 FTS、等回填完成，结果：
- 搜索 `NORMALHOOK`→200 / `ALPHAMARK`→200（FTS 命中）、`GIANTHOOK`→60（LIKE 兜底，巨行）
- DB 层用 **MATCH** 验证（外部内容表绝不能用 COUNT 判断）：`MATCH NORMALHOOK`=200、`MATCH ALPHAMARK`=200、
  **`MATCH GIANTHOOK`=0**（巨行确实没进索引）、`xt_fts_skip`=60、水位=460（越过巨块）。

### 教训（外部内容 FTS5 表铁律，下次直接照做）
- **绝不要用 `SELECT rowid FROM fts` / `COUNT(*) FROM fts` 判断「已索引」**：它读的是内容表，返回全部行。

## 文件体积暴涨分析（10/15 晚，用下载的生产库做只读体检）

用户问「一直往 sqlite 存，一两天就 11GB，留 7 天可能超 100G，大文件对性能有影响吗」。

### 实测数据画像（生产下载库 `data/服务器下载的库/xtlog.db` = 11.41GB，WAL 2GB 未刷完→malformed，只读用 `immutable=1` 打开）
- `xt_log_entry_202610` 单表：共 **231,976 行**，message 正文合计 **7.07GB**，平均 30KB、最大 7.67MB。
- 体积严重畸形（这就是「为什么这么大」的答案）：
  - >1MB 的巨行：**597 行 → 3.68GB（占整个 11.4GB 文件 33%）**
  - 100KB~1MB：**11,676 行 → 2.51GB**
  - ≤100KB：**219,703 行 → 0.88GB**
  - **即 0.26% 的行（>100KB 的 12,273 行）占掉 88% 的 message 体积。**
- `xt_config`：本机活库 `data/xtlog.db` 里 `retention.months=0`（= 不清理，永久保留）、`auto_vacuum=0`（删行不回收空间）、`fts.enabled=1`、`ingest.maxChars=65536`。
- 本机活库 `data/xtlog.db`(9.40GB) 有 wal+shm 在跑，是线上实例；98,194 行跨 ~6.25 天 → ~1.5GB/天。

### 巨行来源（关键，已订正）
经读源码确认：`LogTextIngestor.emit()`(150行) 与 `IngestController.pushOne`(136行) **都已调用 `LogSplitter.expand(d, ingestConfig.maxChars())`**，三条通道(FILE/CMD/HTTP)代码层面均套了上限；`readMaxChars`(DataSourceConfig 652行) 在配置缺失/为空/解析失败时**回退 65536**，不会因"没配置"而关闭拆分。
→ 那 597 个 7MB 巨行是**生产机跑旧 jar 时的历史存量**（下载库的 `xt_config` 连 `ingest.maxChars` 这个 key 都没有，而本机活库有 65536，说明生产那台比当前代码老）。
→ **拆分只拦"未来的"巨行，不缩小"已有的"巨行**：把 7MB 行切成 N 条 64KB 行，正文字节数不变，文件体积不降。要把现有 11GB 压小只能靠压缩(C)或保留策略删旧月表(B)。

### 对性能的真实影响（不是「到某尺寸就突然变慢」，而是几个具体瓶颈被放大）
1. **LIKE 兜底全表扫描是最致命的悬崖**：未索引尾段 + skip 行走 `message LIKE '%kw%'`，无索引可用 → 对 100GB 表是秒~分级全扫，且**拿读锁会阻塞 SQLite 唯一写者** → 搜索时落库卡住。FTS MATCH 本身在 100GB 仍亚秒。
2. **VACUUM / 备份又贵又险**：`auto_vacuum=0` 删行不缩文件；要回收得整库 VACUUM（需 ~2× 空闲盘 + 长锁）。`cp` 活库就是这次下载 malformed 的原因——必须 `.backup` / `VACUUM INTO` / 在线备份 API。
3. **单写者锁竞争**：高并发推送时所有 INSERT 串行抢一把锁，`busy_timeout=60s` 让竞争者等待而非失败 → 吞吐上限=单写者能力，量大时延迟尖刺。
4. **FTS5 索引随正文等比膨胀**（trigram 约 0.37× 原文），100GB 正文→FTS 数十 GB，重建/optimize 很重。
- 热路径（FTS MATCH / 按 id 翻页）在 100GB 下仍快，问题集中在上面 4 点。

### 建议排序（先止血再优化）
A. **FILE/CMD 也套 maxChars 拆分**（最大收益）：堵住 7MB 巨行来源，立省 ~3.7GB 且阻止继续涨。
B. **加保留策略**：`retention.months=0` 改成 7/30；但 auto_vacuum=0 下 DELETE 不缩文件 → 要么定期 VACUUM，要么改**按天分表 + DROP 旧天表**（即时回收、契合现有月表设计、无需 VACUUM）。
C. **message 列压缩**（zstd）：7MB 栈轨迹压到 ~200KB，存储/IO/FTS 体积同时降 10~30×。
D. **给 LIKE 兜底加边界**：只在 `id > 水位-N` 的近期行上扫，绝不扫整表。
E. **安全备份**：停服或 `.backup`，别 `cp` 活库。
